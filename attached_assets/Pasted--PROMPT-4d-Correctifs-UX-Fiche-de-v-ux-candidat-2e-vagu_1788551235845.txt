## 2. Disponibilité fonctionnaire : booléen → varchar(50) (P4_08, PRÊT sous 1 réserve mineure)

**Confirmé par Damien le 04/09/2026** : le contrat d'import candidat n'a pas besoin d'une nouvelle
colonne — il doit seulement documenter, pour ce champ existant (non importé), les 3 valeurs
attendues par Passerelle : `OUI`, `NON`, `NON APPLICABLE`.

⚠️ **Réserve mineure** : la demande initiale (P4_08) donnait `Non Concerné` comme 3e valeur ; la
confirmation du 04/09/2026 dit `NON APPLICABLE`. Je retiens `NON APPLICABLE` (formulation la plus
récente) dans ce correctif — à signaler si ce n'est pas le libellé définitif voulu.

**Mapping des données existantes** (non explicitement tranché par Damien, hypothèse par défaut
retenue faute d'indication contraire — à corriger si besoin) : `true → OUI`, `false → NON`,
`NULL → NULL` (reste "non renseigné", distinct de "NON APPLICABLE" qui est une vraie 3e réponse
métier, pas un synonyme d'absence de réponse).

**Correctif** :

```sql
-- Migration SQL, PostgreSQL — conserve les valeurs existantes
ALTER TABLE fiche_de_voeux
  ALTER COLUMN fonctionnaire_dispo_demandee TYPE VARCHAR(50)
  USING (CASE
    WHEN fonctionnaire_dispo_demandee = true  THEN 'OUI'
    WHEN fonctionnaire_dispo_demandee = false THEN 'NON'
    ELSE NULL
  END);
```

**Écran** (vue et modification, `/candidat/voeux` et `/recruteur/candidats/:id` onglet Vœux) :
remplacer le toggle booléen par un sélecteur à 3 valeurs : `OUI`, `NON`, `NON APPLICABLE`. Pas de
valeur par défaut pré-sélectionnée (cohérent avec P4_10 sur le même principe de champ non
pré-rempli).

**Écran vue (lecture seule)** : remplacer le picto booléen actuel par le libellé texte (`OUI` /
`NON` / `NON APPLICABLE` / `—` si NULL) ou un picto à 3 états si un composant existe déjà pour ça
dans l'app (à choix de l'implémentation, tant que les 3 valeurs restent visuellement distinctes).

**Contrat d'interface candidat** (`contrat_interface_import_candidats.md`) : confirmé 04/09/2026 —
pas de nouvelle colonne importée, seulement documenter le nouveau type et les 3 valeurs possibles
(`OUI`/`NON`/`NON APPLICABLE`) — champ non importé (candidat/recruteur-éditable uniquement),
cohérent avec le reste des champs "volontairement absents à l'import" déjà listés dans
`prompt3.txt` §2.

**Test réel avant de livrer** : vérifier la migration sur les fiches de vœux de test existantes
(valeurs `true`/`false` bien reprises en `OUI`/`NON`, `NULL` reste `NULL`), vérifier que le
sélecteur des 3 valeurs fonctionne en vue et en édition, et que la vue candidat (`/candidat/voeux`)
affiche correctement le libellé texte.

## 3. Tooltips d'aide sur la fiche de vœux (P4_09, PRÊT)

cerclée. Au survol (desktop) / tap (mobile), affiche une bulle d'aide (tooltip).

**Contenu** : texte placeholder par champ, format `blabla_01`, `blabla_02`, `blabla_03`... (un
identifiant unique par champ, incrémental) — le texte réel sera fourni par la DCC ultérieurement.

**Stockage recommandé** : une table dédiée (ex. `aide_contextuelle(cle_champ, texte)`), éditable
depuis l'écran Admin référentiels déjà existant (générique, cohérent avec ENF-12 — la DCC doit
pouvoir changer ces textes sans support technique). Si un mécanisme plus simple existe déjà dans le
code pour ce genre de texte statique, l'utiliser à la place — mais il doit rester éditable sans
redéploiement de code.
