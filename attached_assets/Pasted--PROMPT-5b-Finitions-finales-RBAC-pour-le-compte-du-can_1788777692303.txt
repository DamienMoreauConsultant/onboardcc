## 3. Upload réel de pièces jointes (P4_35)

⚠️ **Principe de conception, à respecter précisément** : le code doit fonctionner **sans
modification** quel que soit l'environnement (Replit aujourd'hui, o2switch demain, le serveur DCC
plus tard) — seule la **valeur** d'une variable d'environnement change entre environnements, jamais
le code. Deux responsabilités bien séparées :
- **L'écriture du fichier** se fait toujours en **local**, relative au dossier de l'application
  (ex. `./uploads/`, créé automatiquement s'il n'existe pas) — peu importe où l'app tourne à ce
  moment-là, elle écrit sur son propre disque. Aucune dépendance à un chemin absolu ni à un serveur
  distant.
- **L'URL publique** utilisée pour construire le lien stocké en base vient de
  `PIECE_JOINTE_STORAGE_URL` (variable d'environnement déjà posée par A22) — c'est la **seule**
  chose qui change entre Replit (ex. `https://<domaine-replit>/uploads/`) et o2switch (ex.
  `https://passerelle.dm-informatique.fr/uploads/`) et le futur serveur DCC.

**Hypothèse de stockage confirmée par Damien** : pas d'intégration API Google Drive réelle (aurait
demandé une configuration OAuth/compte de service distincte) — stockage local classique.

**Valeur de `PIECE_JOINTE_STORAGE_URL` sur Replit (dev)** : si elle n'est pas déjà définie, déduis-la
automatiquement de l'URL de base déjà utilisée ailleurs dans l'app pour générer des liens cliquables
(emails de réinitialisation de mot de passe, invitations de compte, prompt6) plutôt que de demander
à Damien de la saisir manuellement — ex. `${APP_BASE_URL}/uploads/` si une variable de ce type
existe déjà. Sers le dossier `uploads/` en statique à ce même chemin (`/uploads`).

### 3.1 Mécanisme

Sur la popup générique de transition (`conception.md` §6.1.2, utilisée notamment pour
`decisionDCC()`, `mettre_en_lien()`... — voir capture Damien), remplace les 2 champs texte libre
"URL de la pièce jointe 1/2" par 2 boutons "Choisir un fichier" :

1. L'utilisateur clique, le navigateur ouvre le sélecteur de fichier natif (`<input type="file">`).
2. Formats acceptés, vérifiés côté client **et** côté serveur (jamais l'un sans l'autre) : PDF,
   JPEG, PNG (même liste que le correctif `prompt5` déjà en place pour la validation MIME) — rejette
   avec un message clair si le format ne correspond pas.
3. Taille maximale : réutilise la même limite que l'import CSV (5 Mio) sauf avis contraire — à
   confirmer si une limite différente est souhaitée pour ce type de fichier.
4. Si le format est valide : renomme le fichier (ex. `{crm_key ou id}_{JJMMAAAA}_{HHMMSS}.{ext}`,
   cohérent avec l'exemple donné par Damien) et l'**écrit localement** dans le dossier `uploads/` de
   l'application (`fs.writeFile`, pas d'appel réseau vers un autre serveur).
5. Sert ce dossier en statique via Express (`app.use('/uploads', express.static(...))` ou
   équivalent) — c'est ce qui permet à `PIECE_JOINTE_STORAGE_URL` + nom de fichier de fonctionner
   comme une vraie URL accessible, quel que soit l'environnement.
6. Construit l'**URL complète** en concaténant `PIECE_JOINTE_STORAGE_URL` (env var) + nom de fichier
   généré, et la stocke dans `etape.url1_piece_jointe` / `url2_piece_jointe` (colonnes déjà
   existantes, `VARCHAR(250)` — vérifie que la longueur reste suffisante avec le nouveau format de
   nom de fichier).
7. **Le champ "Description des pièces jointes" devient obligatoire dès qu'au moins un fichier est
   choisi** (aucune contrainte s'il n'y a aucune pièce jointe).

### 3.2 Affichage

Partout où `url1_piece_jointe`/`url2_piece_jointe` sont déjà rendus cliquables (déjà corrigé par
A22 — onglet "Progression et documents") : garde le même principe, l'utilisateur voit un bouton/lien
nommé (ex. "📎 Voir la pièce jointe 1"), jamais l'URL brute affichée en texte.

### 3.3 Test réel avant de livrer (sur Replit, dès maintenant)

1. Uploader un PDF valide → vérifie le renommage, l'écriture locale dans `uploads/`, l'URL complète
   en base (construite avec la valeur actuelle de `PIECE_JOINTE_STORAGE_URL` sur Replit), le lien
   cliquable et accessible côté affichage.
2. Tenter d'uploader un format non toléré (ex. `.exe`) → rejeté avec message clair, côté client ET
   en rejouant l'appel API directement (pour confirmer que la validation serveur n'est pas
   contournable).
3. Tenter de confirmer une transition avec une pièce jointe choisie mais sans description → doit
   être bloqué.
4. Confirmer une transition sans aucune pièce jointe et sans description → doit fonctionner
   normalement (pas de régression sur le cas sans pièce jointe).

**Note pour le déploiement futur (o2switch, puis serveur DCC)** : aucune action de code à prévoir —
seulement créer le dossier `uploads/` sur le nouveau serveur (permissions `755`, `.htaccess` avec
`Options -Indexes` pour empêcher le listing public) et mettre à jour `PIECE_JOINTE_STORAGE_URL`
dans le `.env` du nouvel environnement.
