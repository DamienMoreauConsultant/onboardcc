## 1. Contexte

Le formulaire réel de fiche de poste DCC attend un **qualificatif** pour le billet d'avion
("Partenaire", "DCC", ou occasionnellement "Volontaire" qui paie lui-même) — pas un simple
Oui/Non. La colonne `fiche_de_poste.billet_avion` (BOOLEAN) est remplacée par
`fiche_de_poste.id_type_billet_avion` (FK vers la nouvelle table `type_billet_avion`),
**administrable par l'Admin** au même titre que les autres référentiels (pays, durée...).

## 2. Backend

1. Ajoute `type_billet_avion` à la **liste blanche** des tables administrables
   (`routes/admin.js`, même mécanisme que les référentiels existants, prompt1) — colonnes
   `crm_key`, `designation`, `active`, comme les autres.
2. Toutes les routes/requêtes qui lisent ou écrivent `fiche_de_poste.billet_avion` (écran détail
   poste, import CSV) doivent être basculées sur `id_type_billet_avion` (jointure vers
   `type_billet_avion.designation` pour l'affichage, résolution par `crm_key` pour l'import).
3. **Contrat d'import poste** (prompt2.txt, colonne 21 `billet_avion`) : passe de "Optional
   (booléen)" à "Optional — résout `type_billet_avion.crm_key` → `id_type_billet_avion`", même
   principe que les autres colonnes à résolution référentielle (pays, hébergement...).
4. Une fois le code basculé et testé, **supprime l'ancienne colonne**
   `fiche_de_poste.billet_avion` (BOOLEAN) — elle ne doit plus être utilisée nulle part :
   ```sql
   ALTER TABLE fiche_de_poste DROP COLUMN IF EXISTS billet_avion;
   ```

## 3. Écran Admin référentiels

Ajoute "Type de billet d'avion" à la liste déroulante "Choisir un référentiel" de

## 4. Visibilité CHZ sur les postes (Correctif DCC A23, tranché 31/08/2026)

Un utilisateur avec `role_applicatif = 'RECRUTEUR'` **et** `role_contact = 'CHZ'` doit avoir les
**droits d'action** d'un Recruteur classique (routes `/recruteur/...` complètes), mais une
**visibilité restreinte** aux seuls postes où il apparaît dans `gere_poste` — comme un CM,
malgré des droits plus larges.

Ajoute ce filtre conditionnel sur `GET /api/postes` (liste) et `GET /api/postes/:id` (détail) :
```sql
-- Pseudo-code : si l'utilisateur connecté a role_contact = 'CHZ', restreindre aux postes
-- où il apparaît dans gere_poste. Sinon (REC classique), aucune restriction.
WHERE (:role_contact != 'CHZ'
       OR id_poste IN (SELECT id_poste FROM gere_poste WHERE id_contact = :id_contact))
```
Réutilise la même jointure que celle déjà construite pour `/cm/postes` (prompt2 §4) — pas de
nouvelle logique de fond, juste une condition supplémentaire sur les routes recruteur existantes.
**`/recruteur/candidats` n'est pas concerné** (pas de notion de rattachement à un poste précis
côté candidat, un CZ voit tous les candidats comme un Recruteur classique).
