Crée une application web full-stack nommée **onboardcc** pour la DCC (Délégation Catholique
pour la Coopération), ONG française gérant des missions de volontariat international (VSI et
bénévolat). L'application digitalise le processus de recrutement et d'affectation des candidats
sur des postes à l'étranger. C'est un **prototype 2** — il reprend un premier prototype (Bolt)
dont les retours ont produit une spécification détaillée (fournie dans les prompts suivants).

---

## Stack technique (obligatoire, ne pas modifier)

- **Frontend** : React 18 + Vite + Tailwind CSS
- **Backend** : **Node.js 18+ avec Express** — un seul langage (JavaScript) sur tout le projet,
  front et back, décision actée en conception.md §7.2 (revue le 09/07/2026)
- **Base de données** : PostgreSQL, accès via la librairie `pg` (requêtes SQL paramétrées —
  pas d'ORM lourd obligatoire, `pg` brut est suffisant pour ce volume et plus simple à lire
  pour un développeur qui découvre le code)
- **Auth** : `jsonwebtoken` (JWT) + `bcrypt` pour le hash des mots de passe
- **Config** : `dotenv` (fichier `.env` à la racine du backend)
- **HTTP client frontend** : `axios`

## Rôles utilisateurs (RBAC strict — conception.md §5.2, §6.1.1)

| Rôle | Table `contact.role` | Description |
|------|------|-------------|
| Administrateur | ADMIN | Gestion des référentiels (voir module Admin ci-dessous) |
| Recruteur (staff DCC) | — *(porté par `user_`, sans entrée `role` dédiée dans `contact`)* | Gestion candidats, postes, matching, propositions aux CM |
| Chargé de Mission | CM1 / CM2 / CHZ | Validation des propositions sur ses postes |
| Candidat | CAN | Dossier personnel, fiche de vœux, suivi |

Chaque utilisateur (`user_`) a un seul rôle, déduit de `contact.role` associé. Le dashboard
s'adapte automatiquement après connexion selon ce rôle.

**Règle métier critique — création des comptes candidats (conception.md §6.3.3) :**
Le candidat **ne s'inscrit jamais lui-même**. Son compte `user_` est créé automatiquement par le
backend au moment où le recruteur valide `candidat.valider_appel1()` (voir prompt3) — un email
est envoyé avec un lien de création de mot de passe. Il n'y a **aucune page d'inscription publique**.

**Édition par onglet, jamais par écran entier** (conception.md §6.1.1) : prévoir dès l'architecture
API des routes granulaires par onglet (ex. `PATCH /api/candidats/:id/etat-civil`,
`PATCH /api/candidats/:id/voeux`) plutôt qu'une route unique `PUT /api/candidats/:id` qui écrirait
tout l'objet.

## Authentification (conception.md §6.1.1, §8.1)

- `POST /api/auth/login` → `{ login, password }` → vérifie le hash bcrypt, retourne un cookie
  contenant le JWT + le corps `{ role, id_contact, id_candidat (si CAN), nom, prenom }`
- `POST /api/auth/changer-password` → `{ ancien_password, nouveau_password }` (auth requise)
- Middleware `requireRole(roles)` sur toutes les routes protégées, qui vérifie le JWT (cookie) et
  le rôle qu'il porte — bien commenter ce middleware, c'est la pièce de sécurité centrale
- Payload JWT : `{ id_user, role, id_contact, id_candidat }`, durée **8h**, `JWT_SECRET` ≥ 32 caractères
- **Le JWT n'est jamais stocké en `localStorage`** (règle non négociable, conception.md §8.1) :
  cookie `HttpOnly; Secure; SameSite=Strict` posé par le backend à la connexion
- CORS configuré en liste blanche explicite (`cors({ origin: FRONTEND_URL, credentials: true })`,
  jamais `origin: "*"`)

## Module Admin — Référentiels (conception.md §5.2, ENF-12)

> **Contrainte ENF-12 :** la DCC n'a pas de ressource IT dédiée et subit un fort turnover. Cet écran
> doit être **utilisable sans formation technique**. Ne construis **pas** 12 écrans différents un par
> un — construis **un seul composant générique réutilisable**, paramétré par table, pour limiter la
> charge de maintenance.

### Tables administrables (toutes déjà créées et peuplées par `prompt_0_sql.sql`)

`langue`, `region`, `pays`, `environnement`, `duree`, `hebergement`, `domaine`, `competences`,
`notoriete_dcc`, `etat_poste`, `etat_opportunite`, `niveau_langue`, `stages`.

⚠️ **Exception : `etat_candidat`.** Cette table est administrable en lecture (voir ses libellés)
mais ses lignes (les 11 états CRE/AP1/AP2…) sont **structurantes pour toute la logique applicative**
(prompt3) — ne permets **ni ajout ni suppression** de ligne sur cette table depuis l'écran Admin,
seule l'édition du libellé `designation` et du `delais_de_reponse` est autorisée.

### Écran — `/admin/referentiels` *(rôle ADMIN uniquement)*

- Menu déroulant "Choisir un référentiel" listant les tables ci-dessus (nom lisible, pas le nom
  technique de la table — ex. "Régions" plutôt que "region").
- Tableau des lignes existantes : colonnes `crm_key`, `designation`, `active` (case à cocher).
- Actions : **Ajouter une ligne**, **Modifier** (crm_key + designation + active), **Désactiver**
  (jamais de suppression physique — toujours `active = false`, car ces référentiels sont référencés
  par clé étrangère depuis des postes/candidats existants ; une vraie suppression casserait ces liens).
- Pour `pays` : champ supplémentaire "Région" (liste déroulante des régions existantes).
- Pour `duree` : champs supplémentaires "Statut" (VSI/Bénévolat) et "Niveau" (nombre, sert au calcul
  d'écart du scoring, prompt4 — expliquer cette utilisation dans un texte d'aide sous le champ).
- Pour `environnement` : idem, champ "Niveau".
- Pour `domaine`/`competences` : `competences` doit proposer un menu déroulant "Domaine parent".
- Pour `stages` : champs `type_stage`, `date_debut`, `date_fin`, `voeux_definitif_ouvert`.

### API backend (`routes/admin.js`)

Routes génériques paramétrées par nom de table (liste blanche stricte des tables autorisées
ci-dessus — **ne jamais construire une requête SQL en insérant le nom de table venant du frontend
sans le valider contre cette liste blanche**, sinon risque d'injection SQL) :

```
GET    /api/admin/referentiels/:table
POST   /api/admin/referentiels/:table
PATCH  /api/admin/referentiels/:table/:id
```

Toutes protégées par `requireRole(['ADMIN'])`.
